Missing Data Scenarios: CPU Activity Monitoring (Target Variable: usr)
Scenario 1: MCAR (Missing Completely at Random)
System Context: UDP Network Packet Loss. The Sun Sparcstation server transmits its performance logs every 5 seconds over the university's local area network (via UDP protocol) to a central monitoring dashboard. Due to occasional, random network congestion and packet collisions on the campus network, some telemetry logs are dropped in transit.

Statistical Phenomenon: The missingness of the usr (user-mode CPU utilization) is entirely unpredictable. It has absolutely no statistical relationship with the actual CPU load, memory usage, system calls, or any other system state at that given moment.

Scenario 2: MAR (Missing at Random)
System Context: Interrupt-Driven Buffer Overflow. The monitoring daemon uses a fixed-size internal buffer to temporarily store log entries. When the server experiences a massive surge in underlying system calls (measured by the fully observed variable scall—e.g., due to heavy I/O operations or frequent kernel interrupts), this buffer quickly overflows with high-priority system events. Consequently, lower-priority user-level metrics like usr are frequently dropped to clear the queue.

Statistical Phenomenon: The correlation matrix will show that the missingness indicator (M_usr) has a strong, visible positive correlation with the fully observed variable scall. The higher the frequency of system calls, the systematically higher the probability that the usr data is missing.

Scenario 3: MNAR (Missing Not at Random) - The Computer Science Trap
System Context: Daemon Starvation & Resource Exhaustion. The monitoring daemon responsible for recording CPU activity is itself a process that requires CPU resources to operate. When the server experiences extreme, paralyzing compute loads—such as a user accidentally executing an infinite loop (e.g., a fork bomb) or an extremely intensive scientific simulation—the true usr (CPU utilization) skyrockets to 99% - 100%. During this state of extreme resource starvation, the monitoring daemon is deprived of the CPU time slices necessary to execute its own logging function, causing it to freeze or fail silently.

Statistical Phenomenon: The system fails to record the data precisely because the CPU load is at its absolute maximum limit. The occurrence of missingness directly depends on the unrecorded, extreme value itself. In a correlation matrix where the true usr values are hidden, this creates a deceptive illusion of MCAR, leaving no visible statistical footprint for analysts to rely on.
